## 1. `TSK-000782`

### 보존 제안

운영 table에 존재하지 않는 ID를 임의 생성하지 않는다.

1. `overlay.taskPatch["TSK-000782"]`는 `compliance_task` UPDATE 대상에서 제외한다.
2. 원본 `.data/overlay.json`은 그대로 보존한다.
3. 실제 import를 만들 때 별도 provenance 산출물에 아래 원문을 변형 없이 묶는다.
   - `taskPatch` 원문 1건
   - 연결된 `inspection` 원문 1건
   - 연결된 `log` 원문 2건
   - `_removed_compliance_task`, `_removed_task_approval_patch`, `_removed_evidence`, `_removed_duty_assignment`의 원본 위치와 SHA-256
4. DB 안에도 보존해야 한다면 기존 운영 table에 억지로 넣지 말고 별도 provenance table을 새 migration으로 정의한다. 최소 필드는 `source_path`, `source_section`, `source_key`, `payload_json`, `reason`이다. 원문 JSON을 그대로 저장하고 운영 FK는 걸지 않는다.

관련 `log` 2행은 삭제된 대상에 대한 역사적 감사기록으로서 `audit_log`에 남길 수 있다. 반면 `inspection` 1행을 운영 `inspection`에 둘지 provenance로 격리할지는 별도 결정이 필요하다. FK가 비활성이라는 이유만으로 운영 orphan을 자동 허용하지 않는다.

## 2. `audit_log`

### 현재 PostgreSQL 물리 구조

Railway 배포 검증 기록은 `adoms2.audit_log`가 9개 column, 0행임을 실측했다. 배포된 `db/migrations/0001_tables.sql:89-98`의 9개 column은 다음과 같다.

| column | 현재 물리 타입/속성 | 근거 |
|---|---|---|
| `log_id` | `bigint GENERATED BY DEFAULT AS IDENTITY` | 배포 migration, 활성 PK |
| `table_name` | `text` | 배포 migration |
| `row_key` | `text` | 배포 migration |
| `action` | `text` | 배포 migration |
| `changed_by` | `text` | 배포 migration |
| `changed_at` | `text` | 배포 migration |
| `before_json` | `text` | 배포 migration |
| `after_json` | `text` | 배포 migration |
| `note` | `text` | 배포 migration |

기존 실행 DDL과 필드대장도 같은 9개 이름을 사용한다. 필드대장 의미는 `table_name=표 이름`, `row_key=행 열쇠`, `changed_by=바꾼 사람`, `changed_at=바꾼 일시`, `before_json/after_json=변경 전후 값`, `note=비고`다 (`(명세)운영DB_필드대장_20260922.csv:58-66`). 기존 DDL의 원래 타입은 `changed_at timestamptz`, `before_json/after_json jsonb`지만 현재 migration은 1차 호환 원칙에 따라 `text`로 배포됐다.

### overlay 241행의 실제 구조

모든 값은 문자열이며 key별 실측은 다음과 같다.

| overlay key | 존재 행 | 누락 행 | 존재하지만 `""`인 행 | 비고 |
|---|---:|---:|---:|---|
| `at` | 241 | 0 | 0 | 모두 날짜 parsing 가능, 값 중복 0 |
| `by` | 241 | 0 | 0 | 작성자/행위자 |
| `action` | 240 | 1 | 0 | 1행은 provenance 메모형 행 |
| `target` | 240 | 1 | 0 | 208행은 `prefix:key`, 32행은 `TSK-*` 단독 값 |
| `note` | 240 | 1 | 217 | 존재하는 빈 문자열은 NULL로 바꾸면 안 됨 |
| `what` | 1 | 240 | 0 | `.data/overlay.json:1973`; 이 행에는 `action`, `target`, `note`가 없음 |

`what` 1행은 화면 시험 회차와 관련 자료를 지운 사실 및 원본 백업 위치를 기록한 provenance 문장이다. 이를 `note`에 합치면 원래 key 구분이 사라지므로 손실 없는 이관이 아니다.

### 근거가 있는 mapping

| overlay | 현재 `audit_log` | 판정 |
|---|---|---|
| `at` | `changed_at` | 가능. 필드대장의 “바꾼 일시”와 앱의 timestamp 값 의미가 일치한다. 현재 물리 타입이 `text`라 문자열을 변환할 필요도 없다. |
| `by` | `changed_by` | 가능. 필드대장의 “바꾼 사람”과 일치한다. 과거 README와 export script의 `actor` 표기는 현재 DDL과 불일치하는 구식 이름이다. |
| `action` | `action` | 가능. 이름과 의미가 동일하다. key가 없는 1행은 NULL로 두되, 존재하는 값을 바꾸지 않는다. |
| `note` | `note` | 가능. 이름과 의미가 동일하다. 217개의 `""`는 그대로 빈 문자열로 보존한다. |
| `target` | 없음 | 불가능. `table_name`과 `row_key`로 분리하라는 근거가 없다. 32개 `TSK-*` 값에는 table 접두사도 없다. 전체 문자열을 `row_key`에 넣는 규칙도 기존 코드/DDL에 없다. |
| `what` | 없음 | 불가능. `note`, `before_json` 또는 `after_json`으로 합치라는 근거가 없다. |
| 생성 식별자 | `log_id` | 가능. overlay에는 식별자가 없으며 DDL이 identity 생성을 명시한다. |

따라서 현재 9개 column만으로 241행을 손실 없이 이관할 수 없다. `target`과 `what`을 버리거나 다른 column에 합치는 방안은 채택할 수 없다.

### 기존 코드와의 구조 충돌

- `lib/data.ts:359-361`의 CSV 모드는 241행 전체를 저장 순서대로 반환한다.
- 같은 함수의 DB 모드는 `order=at.desc&limit=100`을 사용한다. 현재 table에는 `at`이 없으므로 그대로는 조회 오류가 난다.
- 앱 화면은 `l.at`, `l.by`, `l.action`, `l.target`, `l.note`를 직접 읽는다 (`app/ceo/page.tsx:53-57`, `app/evidence/page.tsx:251-252`).
- 과거 `scripts/export_overlay.mjs:79-80`은 `(at, action, target, actor, note)`에 INSERT하도록 작성됐지만 이 column들은 현재 DDL에 없다. 이는 현 migration에 사용할 수 있는 mapping 근거가 아니라 과거 구조 불일치의 증거다.
- `at` 241개는 서로 중복되지 않지만 overlay 저장 순서는 완전한 시간 내림차순이 아니다. 마지막 `what` 행의 `at`은 `2026-09-26`이므로 DB에서 시간순 정렬하면 현재 배열의 마지막 위치가 바뀐다.
- DB 경로의 `limit=100`도 CSV 경로의 241행 전체 반환과 다르다. column 문제만 해결해도 화면 결과가 자동으로 같아지지는 않는다.

### 최소 스키마 변경 제안

아직 SQL을 작성하거나 실행하지 않는다.

**데이터 자체의 손실 없는 저장만을 위한 최소 변경**은 `target text`, `what text` 두 column을 추가하는 것이다.

- `at → changed_at`
- `by → changed_by`
- `action → action`
- `note → note`
- `target → 새 target`
- `what → 새 what`

이 안은 저장 손실은 없지만 현재 앱이 기대하는 `at`과 `by` 이름 및 `order=at` query는 해결하지 않는다. 나중에 앱 조회 mapping을 변경해야 한다.

**앱 코드를 바꾸지 않는 schema-only 호환 최소안**은 정확한 overlay 이름의 `at`, `by`, `target`, `what` 네 column을 추가하는 것이다. `at`과 `by`는 각각 `changed_at`, `changed_by`와 같은 값을 보존해야 하며, 이중 기록의 불일치를 막으려면 generated column 또는 명시적 동기화 규칙이 필요하다. 그래도 `limit=100`과 특별 provenance 행의 정렬 차이는 남는다.

권고 순서는 다음과 같다.

1. 정본 column은 기존 DDL 의미가 분명한 `changed_at`, `changed_by`로 유지한다.
2. 손실 방지를 위해 `target`, `what`을 독립 column으로 추가한다.
3. DB 전환 시 앱에서 `changed_at/changed_by`를 `at/by`로 명시적으로 mapping하고, 241행 반환 범위와 원본 순서를 어떻게 보존할지 별도 결정한다.

이는 column 추가 및 향후 조회 mapping에 대한 제안일 뿐이다. migration, import script, 앱 코드는 아직 변경하지 않는다.

## 결론

- `TSK-000782`: D. 삭제된 업무의 오래된 overlay patch. 운영 `compliance_task` import에서는 제외하되 원문과 연결 기록을 provenance로 보존하는 것이 타당하다.
- `audit_log`: 현재 schema로는 `target` 240개와 `what` 1개를 근거 있게 저장할 곳이 없어 손실 없는 이관이 불가능하다.
- 최소 데이터 보존 schema 변경: `target text`, `what text` 추가.
- 현재 앱 무수정 호환까지 schema만으로 해결하려면 `at`, `by` 호환 column도 필요하다. 다만 100행 제한과 배열 순서 차이는 별도 결정 대상이다.
- 두 제안 모두 미적용 상태다. 최종 적용안이 확정되기 전까지 WORKLOG에는 새 결정을 추가하지 않는다.
