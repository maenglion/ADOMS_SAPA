## Source-name collision review

`log_id` also appears in `usf_ceo_log`, including a value in `overlay.tables.usf_ceo_log`. That is a separate table's text business identifier with values such as `CLOG-*`. It does not reference `audit_log.log_id` and must remain in `usf_ceo_log` INSERTs.

## Evidence

- The deployed catalog reports `audit_log.log_id` as `bigint`, `NOT NULL`, `is_identity = YES`, `identity_generation = BY DEFAULT`.
- `db/migrations/0001_tables.sql` declares `bigint GENERATED BY DEFAULT AS IDENTITY`.
- Legacy executable DDL and the field register declare the same role as `bigserial primary key` and describe it as the audit record number.
- `db/import/BLOCKER_RESOLUTION.md` previously established that `overlay.log` has no generated identifier and that the database may create `log_id`.
- Repository-wide exact-name search found no data relationship that points to `audit_log.log_id`.

## Importer rule

The importer reads both `is_identity` and `identity_generation` from the live catalog.

- If no source row owns the identity field, it excludes that field from INSERT.
- If every source row owns a `BY DEFAULT` identity field, it preserves and inserts those source identifiers.
- If only some rows provide an identity field, import is blocked. It does not bind `NULL` or generate replacement identifiers.
- If source identifiers exist for an `ALWAYS` identity, import is blocked pending an explicit preservation decision.

This rule prevents the `audit_log.log_id` failure without treating unrelated text identifiers such as `usf_ceo_log.log_id` as database-generated columns.
